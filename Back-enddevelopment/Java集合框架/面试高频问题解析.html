一、整体说明：如何回答集合面试题？

  • 先说应用场景：常用在哪、为什么选它
  • 再说底层结构：数组/链表/跳表/红黑树/分段等
  • 接着说时间复杂度：增删改查、迭代、扩容代价
  • 最后补充线程安全/扩容/树化等细节
    👉 答题模板：场景 → 原理 → 性能 → 线程安全 → 边界/坑

快速复杂度卡片

  • 数组类：随机读 O(1)，中间插入/删除 O(n)
  • 链表类：随机读 O(n)，头尾插删 O(1)
  • 哈希表：均摊 O(1)，碰撞/退化需说明
  • 树（红黑树）：查/增/删 O(log n)
  • 阻塞队列：入/出均摊 O(1)，满/空阻塞

二、HashMap 是如何实现的？底层结构是怎样的？（高频必考 ⭐⭐⭐⭐⭐）

1. 底层结构

  • JDK7：数组 + 单链表（头插，扩容时易形成环）
  • JDK8：数组 + 链表 + 红黑树（尾插，避免环，冲突多时树化）
  • Node<K, V>[] table，字段：hash、key、value、next

2. 重要参数

  • 初始容量：16
  • 负载因子：0.75
  • 阈值 threshold = capacity × loadFactor
  • 树化阈值：链表长度 ≥ 8 且容量 ≥ 64
  • 退化阈值：链表长度 < 6 时红黑树退化为链表
  • 红黑树节点：TreeNode，存父子/前后指针，维持平衡

3. put 流程（JDK8 简化）

  1. 计算 hash 值 & 索引：(h = key.hashCode()) ^ (h >>> 16) 让高位参与，降低碰撞
  2. 如果桶位为空 → 直接放入
  3. 如果 key 已存在 → 覆盖 value
  4. 如果链表长度 ≥ 8 且容量 ≥ 64 → 链表转红黑树
  5. 如果 size 超阈值 → 扩容

4. 扩容机制

  • 新容量为原来的 2 倍
  • 元素要 重新 hash 分布
  • 低位/高位拆分：旧容量最高位为 0 → 落原索引；为 1 → 落原索引+旧容量
  • 扩容代价大 → 预估容量：new HashMap((int)(expectedSize / 0.75f) + 1)
  • 扩容触发时机：插入后 size > threshold（先插后扩）

5. 常见追问

  • 为什么负载因子默认 0.75？
  • 为什么树化阈值是 8？
  • 红黑树什么时候退化回链表？桶中元素 < 6
  • fail-fast：modCount 变化即 CME

6. 典型坑位

  • 负载因子过小浪费空间，过大碰撞重
  • key 未正确重写 hashCode/equals，出现“看似相等但共存”
  • 扩容昂贵：批量插入要提前指定容量
  • 并发用 HashMap 可能死链/数据错乱，需用 ConcurrentHashMap

三、HashMap 和 Hashtable 区别？为什么说 Hashtable 已过时？

1. 主要区别

对比点 HashMap Hashtable

线程安全 否 是（方法级 synchronized）
null key/value 允许 不允许
性能 高（无锁） 低（整表锁）
结构 数组+链表/红黑树 数组+链表
迭代器 fail-fast 不支持 fail-fast
泛型 支持 早期类，泛型体验差
是否推荐 是 否（已淘汰）

2. 为什么 Hashtable 过时

  • 粒度过大：整张表锁
  • 并发效率低
  • 已被 ConcurrentHashMap 取代
  • API 风格陈旧，缺少泛型支持
  • 实际开发：读多写少用 COW/局部锁，常规并发用 ConcurrentHashMap

四、ConcurrentHashMap 如何实现线程安全？JDK7 & JDK8 区别

JDK 7

  • Segment + HashEntry
  • 分段锁，默认 16 段
  • 本质：锁分段数组，每段内部仍是链表
  • 读无锁，写锁段
  • 迭代弱一致：遍历期间可看到部分最新数据

JDK 8

  • Node + CAS + synchronized
  • 链表/红黑树 + 数组
  • 粒度更细：桶级锁 + CAS
  • 无 Segment
  • 扩容：ForwardingNode 标记，迁移时多线程协作搬运
  • 头插改尾插，降低链表反转风险
  • resize 并行迁移，减少长暂停

线程安全手段

  • CAS
  • synchronized
  • volatile
  • 分段桶锁
  • size 统计：LongAdder + 重试，避免全表锁

典型问答

  • get 为什么无锁？value/next 用 volatile，保证可见性
  • put 什么时候加锁？桶首为空时 CAS，否则锁桶按链表/树写入
  • 为什么不用 ReentrantLock？CAS+轻量 synchronized 成本更低
  • 遍历一致性？弱一致，不抛 CME

五、ArrayList 和 LinkedList 区别？哪些场景适合使用 ArrayList？

核心区别

对比点 ArrayList LinkedList

底层结构 动态数组 双向链表
随机访问 快 O(1) 慢 O(n)
头部插入 慢（整体搬移） 快
中部插入 需搬移元素 需遍历找到节点
尾部插入 均摊 O(1) O(1)
删除 搬移后续元素 改指针
内存占用 小 大（额外指针）
迭代方式 for 索引/迭代器 迭代器或 ListIterator
fail-fast 支持（modCount） 支持（modCount）
缓存友好 高（连续内存） 低
扩容策略 1.5 倍扩容 节点分配，无扩容
线程安全 不安全 不安全

使用场景

✔ 随机访问多 → ArrayList
✔ 插入删除多 → LinkedList
✔ 频繁遍历 → ArrayList
✔ 需要队列/双端 → 优先 ArrayDeque（更快、无额外指针）
✔ 读多写少且并发 → CopyOnWriteArrayList
⚠ LinkedList 随机访问不可控，面试可强调“总体性能弱于数组结构”

面试口诀：读多写少用数组，插入删除用链表

六、Set 是如何保证唯一性的？必须重写哪些方法？

保证唯一性的步骤

  1. 调用 hashCode() 定位桶
  2. equals() 判断是否”相等”
  3. 相等 → 认为重复，不加入
  4. 不等 → 插入

必须重写

  • hashCode()
  • equals()

建议：equals 相等时 hashCode 必须相同；可用 IDE 自动生成
若类可变，参与比较的字段变化会破坏集合语义，尽量设计为不可变或勿作 key

经典错误回答（要避免 ❌）

“Set 自动去重”
👉 一定要答：依赖 Hash 算法 + equals 比较

七、HashSet 为什么要求重写 hashCode 和 equals？

正确答案

因为：

  • HashSet 底层是 HashMap
  • 元素存到 hash 桶 中
  • 需要：
    • hashCode() → 定位桶
    • equals() → 判断相等性

如果不重写会怎样？

  • 逻辑相同对象被认为不同
  • 会出现”看起来重复但能存进去”
  • 迭代/删除时用的 equals 判断，易出现删不掉/重复展示
  • 一致性要求：相等则 hash 相等，否则分桶错位

八、TreeMap 和 TreeSet 的底层结构是什么？

  • TreeMap：红黑树
  • TreeSet：基于 TreeMap 实现

排序方式

  • 自然排序（Comparable）
  • 定制排序（Comparator）

注意

⚠ equals 不影响 TreeSet 唯一性
✔ compareTo / compare 决定是否重复
✔ Comparator/Comparable 需满足自反、反对称、传递，避免排序异常或“看似重复却能存”

  • compare 返回 0 视为重复，不再插入
  • 自定义 Comparator 可实现倒序/多字段排序

九、CopyOnWriteArrayList 的底层原理和应用场景是什么？

1. 底层原理

  • 写时复制
  • 每次写操作：
    • 复制整个数组
    • 修改新数组
    • 替换旧数组
  • 读操作无需加锁，返回快照；迭代器不支持修改

2. 适用场景

✔ 读多写少
✔ 白名单/黑名单
✔ 缓存数据频繁读取
✔ 配置中心/订阅列表等低写场景

3. 缺点

  • 占用内存大
  • 数据不实时一致
  • 大对象复制成本高，写放大明显
  • 不适合低延迟高写入场景
  • 写操作必须获取锁，写频繁时性能骤降

十、Java 中的阻塞队列有哪些？适用于哪些场景？

常见阻塞队列

  • ArrayBlockingQueue（数组）
  • LinkedBlockingQueue（链表）
  • PriorityBlockingQueue（优先级）
  • DelayQueue（定时）
  • SynchronousQueue（无缓冲）
  • LinkedTransferQueue（转移/直通）

应用场景

  • 生产者-消费者模型
  • 任务队列
  • 线程池
  • 限流/削峰：固定容量队列
  • 定时任务：DelayQueue
  • 直通交付：SynchronousQueue/LinkedTransferQueue

十一、为什么不建议使用 Collections.synchronizedList()？

原因

  • 粒度过大：方法级锁
  • 迭代仍不安全
  • 并发效率低
  • 容易抛 ConcurrentModificationException
  • 读多写少时锁竞争无意义

替代方案

✔ CopyOnWriteArrayList
✔ ConcurrentLinkedQueue
✔ 并发低/历史代码：Collections.synchronizedList(new ArrayList<>()) 勉强兜底
✔ 若需定长阻塞：ArrayBlockingQueue

十二、为什么 ArrayBlockingQueue 适合限流场景？

原因

  • 固定容量
  • put 满 → 阻塞
  • take 空 → 阻塞
  • 公平锁可选，避免饥饿
  • 出入 O(1)，无链表节点分配开销

👉 天然限流器

十三、HashSet 如何保证元素唯一？HashSet 与 TreeSet 区别

HashSet

  • 哈希表结构
  • 无序
  • 依赖 hashCode + equals

TreeSet

  • 红黑树
  • 有序
  • 依赖 compare / compareTo
  • 性能：增删查 O(log n)，可按范围/首尾快速定位

面试作答万能模板（直接背）

先结构 → 后原理 → 再性能 → 最后线程安全

示例

“HashMap 如何实现？”

  • 底层结构：数组 + 链表 + 红黑树（JDK8 尾插）
  • 核心参数：容量、负载因子、阈值、树化/退化阈值
  • 关键点：扰动 hash、桶内冲突处理、扩容拆分优化
  • 性能：均摊 O(1)，碰撞多退化 O(n)，树化 O(log n)
  • 线程安全：不安全，推荐 ConcurrentHashMap 或加锁包装

结尾补一句最佳实践/坑位：“并发场景避免用 HashMap，批量插入提前估算容量”
