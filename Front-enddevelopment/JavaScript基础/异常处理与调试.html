异常处理与调试

  • FRONT-ENDDEVELOPMENT
  • JAVASCRIPT基础
  • 异常处理与调试

目标：学会正确抛出与捕获错误，理解 JS 内存管理与垃圾回收基本原理，能使用浏览器开发者工具（以 Chrome DevTools 为例）排查内存泄漏和性能瓶颈。

1. 错误与异常基础

1.1 错误的几种来源

  • 语法错误（SyntaxError）：代码不能被解析（如少了括号），在执行前就抛出。
  • 运行时错误（Runtime Error）：代码语法正确，但在执行时出错（如访问 undefined.xxx）。
  • 逻辑错误：代码能跑但结果不符合预期，需要通过调试/测试发现。

1.2 try / catch / finally

  • 结构：
  • 建议：
    • 尽量只包裹可能抛错的最小代码块，避免掩盖问题。
    • 在 catch 中记录足够信息（错误信息 + 场景）便于排查。

1.3 throw 抛出异常

  • 主动中断流程，将错误交给调用者处理：
  • 可以抛出任意类型，但强烈推荐抛出 Error 或其子类（有堆栈信息）。

1.4 Error 对象与自定义错误类型

  • 常见内建错误类型：
    • Error：通用错误
    • TypeError：类型不符合预期（如把非函数当函数调用）
    • RangeError：数值超出有效范围
    • ReferenceError：引用未定义变量
    • SyntaxError：语法错误
  • 自定义错误：
  • 最佳实践：
    • 用错误类型表达“错误类别”（校验、网络、权限等）。
    • 在错误对象中附加必要上下文（如字段名、状态码）。

1.5 异步中的错误处理

  • Promise 链：使用 .catch() 捕获链上的抛错或 rejected。
  • async/await：使用 try...catch 包裹 await。
  • 全局未捕获：
    • 浏览器：window.addEventListener('error', ...)、window.addEventListener('unhandledrejection', ...)
    • Node：process.on('uncaughtException')、process.on('unhandledRejection')

2. 内存管理与垃圾回收

2.1 内存生命周期三阶段

  1. 分配：创建变量/对象/闭包时，JS 引擎在堆或栈上分配内存。
  2. 使用：读写变量、传参、返回值、闭包引用等。
  3. 释放：当内存不再可达（没有引用）时，垃圾回收器在合适时机回收。

2.2 垃圾回收（GC）基本策略

  • 主流 JS 引擎（如 V8）采用可达性（Reachability）+ 分代回收：
    • 从根对象（全局对象、当前执行栈、闭包中的变量等）出发，能到达的都视为“存活”。
    • 新生代/老生代分区：短命对象快速回收，长寿对象迁移到老生代。
  • 不需要手动 free 内存，但要避免无意中保留引用导致对象“永远可达”。

2.3 常见内存泄漏场景

  • 全局变量或挂在全局对象上的引用从未清理。
  • 定时器/事件监听未移除，仍持有对 DOM/大对象的引用：
  • 闭包保留了不再需要的大对象引用。
  • 缓存（如 Map/数组）不断积累从不清理。

2.4 Chrome DevTools 内存调试（基础流程）

  • 打开 DevTools → Memory 面板（或 Performance + memory 勾选）。
  • 常见两种方式：
    • Heap snapshot：
      • 在操作前后分别拍快照，对比对象数量/大小。
      • 关注“Detached DOM trees”、“Retainers”链，找是谁在引用。
    • Allocation instrumentation：
      • 记录在一段时间内的内存分配情况，定位高频分配与未释放对象。
  • 实战步骤示例：
    1. 打开页面，等待稳定 → 记录快照 A。
    2. 执行可疑操作多次（如切换路由、打开弹窗）→ 记录快照 B。
    3. 对比 A/B，看特定类型对象是否持续累积。

3. 性能优化与调试

3.1 常见性能瓶颈类型

  • 频繁/大规模的 DOM 操作或同步布局计算（回流/重绘）。
  • 大量同步 JS 计算导致主线程长时间被阻塞（卡顿、掉帧）。
  • 不必要的网络请求、过大的资源（图片/脚本）。
  • 内存泄漏导致的页面越用越慢、甚至崩溃。

3.2 使用 Chrome DevTools 检查性能

  • Performance 面板：
    • 录制一次用户操作（如滚动/点击），查看主线程火焰图。
    • 关注长任务（>50ms）、频繁的布局/绘制节点。
    • 标记出耗时最大的函数调用栈，针对性优化。
  • Network 面板：
    • 检查请求数量、大小、耗时。
    • 确认是否存在重复请求、未缓存资源、阻塞首屏的脚本。
  • Lighthouse：
    • 生成自动化报告，给出性能/可访问性/最佳实践建议。

4. 速记

  • “try 小块 catch 记录 finally 收尾，不要用大 try 包一切。”
  • “只抛 Error 及子类，给错误类型与上下文，方便排查。”
  • “内存三阶段：分配→使用→释放；泄漏多半是引用没断干净。”
  • “定时器/监听/缓存要记得清理，否则闭包和 DOM 会一直活着。”
  • “性能调试先看 Performance 火焰图，再看 Network 与 Memory 快照。”***
